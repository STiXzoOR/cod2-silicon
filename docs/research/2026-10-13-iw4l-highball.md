# IW4L and Highball: lessons for CoD2 Silicon 0.3

Studied on 2026-10-13. This is a source study, not a runtime comparison. Neither external project was built, installed or executed. Findings are pinned to IW4L `4d65a39376e14390abe21bd9ad24a28c2687e90f` and Highball `fcee4f64b2a9c8f64b2a7cec4b00c833fa07faaa`; their current default branches may differ.

## What each project can teach this port

IW4L is a Rust/Bevy replacement runtime for MW2. It loads retail assets, translates SM3 shader bytecode into WGSL and renders through wgpu. Its gameplay, GSC interpreter, network protocol and demos belong to its own runtime. Highball is a Swift application that installs and coordinates Wine engines, renderer components and game-specific settings. Neither supplies a compatible CoD2 renderer or a proof that this native port works.

CoD2 Silicon already preserves the reconstructed engine behind `src/Mac/DirectX_9` contracts. Its current shader extractor, `src/platform/cod2x_native_shaders.m`, validates 834 shader/constant files from the player's Mac executable, uses SHA-256 and stages replacement under a lock. Those are ARB programs, not IW4L's SM3 bytecode. The useful transfer is how the other projects establish boundaries and evidence.

## Boundaries that should not transfer

IW4L has IW4/IW5/T5/T6 asset lanes, not an inspected IW2 lane. Replacing CoD2 simulation, GSC, networking or demo handling with those systems would change the contracts this port is preserving. The rendering/frontend split is a useful ownership model, not a migration proposal. See [IW4L rendering ownership](https://github.com/vladtrc/iw4L/blob/4d65a39376e14390abe21bd9ad24a28c2687e90f/docs/RENDER.md) and [script support](https://github.com/vladtrc/iw4L/blob/4d65a39376e14390abe21bd9ad24a28c2687e90f/docs/GSC-RUNTIME.md).

Highball's checked-in set contains 40 x86_64 engine manifests requiring Rosetta. Its ARM64 Wine/FEX helper route is an implementation path, not evidence that those manifests ship a native ARM64 engine. DXMT handles D3D10/11; its D3D9 route uses a separate D9VK overlay. Thus Wine or DXMT is not a shortcut to the native CoD2 backend. See [engine manifest](https://github.com/gauthierpiarrette/highball/blob/fcee4f64b2a9c8f64b2a7cec4b00c833fa07faaa/spike/engine-manifest.json), [helper](https://github.com/gauthierpiarrette/highball/blob/fcee4f64b2a9c8f64b2a7cec4b00c833fa07faaa/Sources/HighballKit/WineLoaderHelper.swift) and the renderer-resolution source above.

Source structure is not execution evidence. Highball's [macOS 26 nightly job](https://github.com/gauthierpiarrette/highball/blob/fcee4f64b2a9c8f64b2a7cec4b00c833fa07faaa/.github/workflows/nightly-e2e.yml) is advisory. Its [regression tests](https://github.com/gauthierpiarrette/highball/blob/fcee4f64b2a9c8f64b2a7cec4b00c833fa07faaa/Tests/HighballKitTests/RegressionTests.swift) exercise OS-gating logic, not a verified CoD2 session. IW4L's documented Mac run is likewise a project claim, not a run performed for this study.

## macOS 26 does not replace capability evidence

Apple lists Metal 4 for Apple-silicon Macs running macOS 26 or later. Backend admission must still check the device capabilities actually used; optional presentation, texture and rendering features have distinct limits. The project floor is macOS 26 for both renderers, including OpenGL fallback. Historical plans describing a macOS 13–25 fallback no longer define the support range. See Apple's [Metal capabilities tables](https://developer.apple.com/metal/capabilities/) and [`MTLGPUFamily`](https://developer.apple.com/documentation/metal/MTLGPUFamily).

## Existing Metal work changes the starting point

The integrated release base `7e1851faeee45d45ed8dbf0ded2d8ec813b8e577` contains no native Metal backend. However, donor commit `bf71e8ecd9985a57c69f27edf442516a8dd02074` from `port/metal-cert` contains substantial implementation and reports. The donor is recoverable from the cleanup archive even if its old branch and checkout are removed. Paths in this section refer to that immutable donor, not files already present on the release base.

The implementation includes `src/Mac/Metal/arb_to_msl.cpp` with parser/register-IR/MSL stages, `shader_setup.mm`, `shader_provider.mm`, `shader_archive.mm`, resource/state/target/draw providers, native presentation in `src/platform/macos_metal_present.m`, `tests/metal/`, and `tools/metal/`. ABI-1 integration is documented in `docs/macos-port/metal-interfaces.md`. The donor reports 208 vertex and 209 fragment programs, plus 417 constant-table files: the existing 834-file cache is not 834 shader programs.

`docs/macos-port/reports/WS39-metal-cert.md` explicitly retains GL as default. Its final certification gaps are physical presentation freshness/starvation, absent common per-draw/pass/resource digests and factory counters, and incomplete visible dense FX/combat evidence. The reported capped 1440p and ordinary-soak p99 of 33.334 ms did not meet the 18.333 ms freshness gate. Six-map pixel comparisons remained `certified=false`. A clean 603.599-second admission/leak soak lacked a physical presentation observer, so it did not close that gap. These are historical donor results, not fresh results on the integrated release.

The shader reports also identify 17 original programs rejected by Apple GL. Synthetic arithmetic oracles cover inferred operations, but the report does not claim complete all-program GL semantic equivalence. Preserve that distinction when defining translation coverage; successful compilation cannot replace an oracle.

There are 38 paths changed on both donor and integrated development lines since ancestor `3ef770ba088808f87805ba748839db2ca53e9dad`. This is an overlap count, not a simulated merge-conflict count. Current saved-screen, water, FX and authored map-lighting corrections make old captures stale even where a textual merge succeeds. Relevant current references are `tests/lp64/renderer/saved_screen.c`, `docs/macos-port/reports/WS75-water-fidelity.md`, `docs/macos-port/reports/WS94-map-lighting-fields.md` and `src/PC/EffectsCore/FxSystem.c`.

The first 0.3 work should recover and audit those donor slices against current contracts. A renderer rewrite would discard relevant implementation; merging the whole branch would risk replacing later fidelity and launcher repairs. The [0.3 readiness plan](../plans/2026-10-13-03-metal-readiness-plan.md) makes evidence and reconciliation the first deliverables.
