# Mac size-taking ring constructor reconciliation

Updated 2026-11-05. Entry `mac:0x001f9740` is **intentional**. This audit changes no runtime source.

Exact-entry Mac disassembly identifies `__ZN15CCircularBufferC1Em` at 0x001f9740–0x001f9783. It clears the five 32-bit fields, calls malloc with the requested size, stores the returned pointer, and records the requested capacity even if allocation fails.

The original owner is concrete. `DSound_NewSample` at 0x001f888e obtains a recording-sample descriptor and a Miles sample handle, allocates a 0x14-byte ring object, passes capacity 0xc800 (51,200), and calls this constructor at 0x001f88e0. It stores the object pointer at sample offset 4, the original `mssBuffer` slot. This is voice playback storage.

The Mach-O symbol table contains only `C1Em` at this entry; there is no size-taking `C2` symbol or other executable alias. A raw relative-call/jump scan over every section marked executable, including `__TEXT,__textcoal_nt` and the import jump table, finds only the call at 0x001f88e0 into the constructor's address range. A whole-file scan for little-endian 32-bit addresses into that range finds only symbol/STABS records, with no stored code or data-table pointer. These scans support the identified owner; they are not a claim to have proved arbitrary computed indirect calls impossible.

Native Apple explicitly excludes legacy `mac_play_dsound.c`, `mac_record_dsound.c`, `CAudioRecorder.c`, `CCircularBuffer.c`, and MacMSS providers in `cmake/macos-arm64.cmake`. It selects `src/platform/macos_voice.c`, `macos_audio.c`, and `macos_ring.c`. A fresh client compilation database confirms those selections and retains `src/PC/groupvoice/play.c`; that wrapper's compiled `Sound_NewSample` references `DSound_NewSample`, supplied by the compiled native voice provider.

The replacement owns the complete playback queue lifecycle. Native `DSound_NewSample` clears and initializes an available static `MacVoiceSample`, allocates its native AIL handle, and returns its descriptor. Its embedded 32,768-byte `queue`, `read_cursor`, and `queued` replace the heap ring; `mssBuffer` remains unused. `DSound_UpdateSample` copies into that queue, `DSound_SampleFrame` drains it through native `AIL_load_sample_buffer`, and `DestroyVoice` releases the AIL handle and clears the owner. The native audio provider decodes the submitted data into owned PCM buffers before returning. No ring-constructor call or retained ring-buffer pointer is required by this path.

The changed capacity, explicit queued-byte count, and native playback ownership are backend adaptations, not constructor equality. This specific original allocation is retired by its mapped native playback owner; adding a disconnected size-taking helper would not improve that mapping.

Capture is a separate boundary. Original `CAudioRecorder` calls the default ring constructor at 0x001f8a51 and `Alloc` at 0x001f9429, not this overload. Native microphone capture remains explicitly unavailable in `macos_voice.c`. This verdict neither claims a complete capture implementation nor relies on capture exclusion to explain the size-taking constructor.

Verification: fresh Release arm64 compile commands compiled the unchanged native voice, audio, ring, and groupvoice playback units with zero diagnostics. Compiled symbol dependencies confirm the playback wrapper/provider connection and no ring dependency in the voice provider. The triage and constant helpers were also run; their shared constructor name maps to the default native constructor and does not establish overloaded-constructor equality. No full link, game, audio-device exercise, CI, replay, new test, or new assertion was run or added.

Private evidence is under `~/Library/Application Support/CoD2-native-decomp/recon-ring-sized-constructor.noindex/`, including exact-entry disassembly, the executable/address-reference scan, selected compile commands, source-selection summary, and compile logs. Original disassembly and binaries are not committed.
