# F1 corpse landing angle storage

`G_RunCorpseMove` reused a two-float animation rotation buffer as the output
of `AxisToAngles`, which writes three floats. Native code now reserves a full
`vec3_t` for that output. The legacy declaration stays unchanged behind the
existing `COD2_X64` gate. Baseline engine source is `bd18d2f` (identical for
this file through integration wave5).

Mac authority: `__Z15G_RunCorpseMoveP9gentity_s`, `0x1b0723–0x1b073c`, supplies
a local three-angle output to `AxisToAngles` and passes it to `G_SetAngle`.
The native callee writes pitch, yaw and roll; the original local has room for
all three. No proprietary source or disassembly was copied into this repo.

The production-path fixture `tests/lp64/game/f1_items.c/.py` reproduced an
ASan stack-buffer-overflow in `vectoangles` via `AxisToAngles` on a valid
corpse landing. The write occurs immediately after the 8-byte `rot` array.
The fixture tests flat and 45-degree slope landing angles, position, ground
entity and falling state, plus rotated/pitched root motion, tiny motion and
falling-without-contact controls. Actual production corpse and math functions
run with collision/animation services supplied by the fixture.

Root-motion indexing was an initial false lead: the unchanged baseline passed
those checks and source inspection confirmed correct coordinate writes. A
suspected missing `axis[2]` initialization is also outside the fix: the current
`AxisToAngles` implementation reads only axes0/1, which are initialized. Its
extra assignment was removed before final tests. The final engine change is
only the native buffer size.

Evidence is private under
`~/Library/Application Support/CoD2-native-decomp/F1-items.noindex/`:
`red-landing/run.log` contains the baseline failure; final stock/CoD2x logs
record the final implementation. Sanitizers use assertions and UBSan halt on
error; compilation is sequential using rebased engine flags. Integration validation and review are recorded separately.
