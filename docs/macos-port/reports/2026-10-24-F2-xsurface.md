# F2 xsurface reconciliation

`behavior_changed: false`. Compared all eight entry points in
`src/PC/gfx_d3d/r_xsurface.c` at `06275b3` with the Mac 1.3 i386 instructions.
No production or test changes were warranted for valid model surfaces. The
only changed path is this report.

## Instruction comparison

- `XSurfaceGetNumVerts` (`0xf9a18`), `XSurfaceGetNumTris` (`0xf9a24`) and
  `XSurfaceGetBoneOffset` (`0xf9abe`) sign-extend the corresponding 16-bit
  fields. `XSurfaceGetVertexInfoArray` (`0xf9ab2`) returns the vertex pointer.
  Current typed fields preserve these operations while retaining native
  pointer width.
- `XSurfaceGetTris` (`0xf9a30`) truncates the offset to 16 bits. Zero offset
  copies six bytes per triangle. Nonzero offset duplicates the offset into
  both halves of a 32-bit word and adds it to three words per iteration,
  copying two triangles. Its original loop is a do/while with
  `triCount >> 1` iterations; the current implementation matches. Read-only
  caller-contract inspection found that `XModelReadSurface` rounds odd
  triangle counts upward and appends a degenerate triangle. The other surface
  loader does the same. An odd-count tail copy or zero-count guard would
  change the original operation and was not added.
- `XSurfaceTransferDx7` (`0xf9aca`) and `XSurfaceTransfer` (`0xf9b2c`) return
  for nonpositive counts, advance the source by 64 bytes, and copy positions,
  normals, packed color and UVs. The DX7 destination stride is 36 bytes; the
  other destination stride is 64 bytes and additionally receives position
  W = 1, binormal and tangent. Current typed members and strides match.
- `XSurfaceGetVerts` (`0xf9bca`, through the final jump at `0xf9ff5`) selects
  rigid versus blended vertices using the signed bone offset sentinel -1.
  Rigid vertices rotate optional normals, copy optional UVs, and transform
  positions with the bone's axis and translation. The source advances by
  64 bytes, positions/normals by 12 and UVs by 8. The three inline transform
  helpers preserve the original multiply/add order with FP contraction off.
- The blended path rotates normals with the primary bone only and does not
  write UVs. It first transforms the primary position. If additional weights
  exist, it scales that position by the unsigned byte weight / 256 and adds
  each transformed blend position times its unsigned short weight / 65536.
  Blend records advance by 16 bytes; the next vertex follows those records,
  or advances by 64 when there are no extra weights. Signed 16-bit byte offsets into
  the bone-matrix array and the unnormalized result match the original.
  The Mac literals at `0x32617c` and `0x32640c` were read directly as
  `0x3b800000` (1/256) and `0x37800000` (1/65536).

## Evidence and tests

Private bounded disassembly and literal readings are under
`~/Library/Application Support/CoD2-native-decomp/F2-xsurface.noindex/`.
The inspection used `nm -a` and one bounded
`otool -arch i386 -tV -p <symbol>` extraction per entry point from the owned
Mac binary. Extraction stopped at the next symbol; the final GetVerts
extraction was further trimmed at its actual final jump because the next
unnamed body was not a symbol boundary. No proprietary reference text was
copied into this report or source.

Existing tests inspected: `tests/lp64/renderer/player_skeleton.c` and its
runner include this production file, but the assertions exercise
`R_SkinXModelCmd` through `r_model.c`; they do not directly prove index
copying, vertex transfer or `XSurfaceGetVerts`. Static-model cache fixtures
stub a surface accessor. These tests were neither changed nor rerun for this
report-only unit. No test was added. There is no failing baseline or green
runtime result to claim: the evidence here is instruction comparison.

Verification commands:

```sh
git diff --exit-code 06275b3 -- src/PC/gfx_d3d/r_xsurface.c
git diff --check
```

Both passed. The engine file is byte-identical to the base, so both native
and `COD2_X64=OFF` source remain unchanged without a preprocessing exception.
No compile, full build, game, VM, original execution or capture comparison
was performed. The unavailable Linux object-comparison gate remains
unverified.

## Boundaries

The comparison covers nonnegative valid vertex counts and the loader's even
triangle-count contract. Malformed negative vertex counts are not asserted
identical: the Mac uses an equality-terminated loop after its zero test,
whereas the reconstructed C uses an increasing `i < vertCount` loop. No
valid-input defect was established, and no malformed-input policy was added.
The original nonzero-offset index-copy loop's behavior for zero triangles
was preserved, not exercised. Loaders, optimization, surface allocation and
rendering callers were read only for contracts and remain separate units.

Considered and not built: odd-triangle copying, zero-count index guards,
blended UV filling, weight normalization, and extra coverage-only fixtures.
The first four would alter Mac behavior; the last would add work without a
confirmed behavior change.
