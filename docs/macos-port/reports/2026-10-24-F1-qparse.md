## Changed behavior

`behavior_changed: true`, native stock and CoD2x only.

1. Space-delimited, number and word tokens retain at most 1023 bytes while
   consuming the complete input token. Native previously kept incrementing the
   output index after storage stopped. At exactly 1024 bytes it returned empty;
   beyond that it wrote a terminator outside the token array into parser state.
   The six affected increments include exponent marker, sign and digit output.
2. `Com_GetLastTokenPos` now reports the current token. `Com_UngetToken` restores
   the preceding token position. Native previously returned the previous token
   and moved that previous slot forward during unget. No shared header/layout
   changes were needed: native field names describe previous/current in the
   reverse physical order from Mac, but the parser already updates those named
   fields logically. The getter and unget operations now use those semantics.
3. Leading bytes 0x80–0xff are whitespace in the non-CSV parser, matching Mac's
   signed-byte comparisons. Native's unsigned whitespace check followed by a
   signed bare-token check could return empty without advancing input.
4. The exponent body executes its first iteration unconditionally, as in Mac.
   In punctuation mode `1ex;` yields token `1ex` and leaves `;`. Native yielded
   `1e` and left `x`. This preserves the original malformed-input quirk; no new
   exponent validation, fallback or recovery behavior was introduced. At terminal
   NUL the native loop stops before advancing beyond the terminated input; see
   the explicit memory-boundary follow-up below.

The changes were independently implemented from Mac behavior, with the Linux
1.3 `universal/q_parse.cpp` read-only guide used to identify discrepancies. No
reference source, assembly or decompiler output was copied into the checkout.

## Mac evidence

Owned Mac 1.3 i386 executable, inspected with `nm -a` and `otool -arch i386 -tV`:

- `Com_ParseExt`, `__Z12Com_ParseExtPPKci`, `0xae056`: space-delimited stores at
  `0xae2c0–0xae2cb` increment the stored length only through 1023, then the
  consumption-only loop at `0xae2d1` advances input. Number stores/consumption
  at `0xae40e–0xae451`, exponent stores at `0xae553–0xae59f`, and word path at
  `0xae465–0xae4a4` follow the same bounded stored-length semantics.
- `Com_GetLastTokenPos`, `__Z19Com_GetLastTokenPosv`, loads `0x3482a4` at
  `0xae04f`. Normal parsing saves the preceding value to `0x3482a8` and writes
  the current input position to `0x3482a4` at `0xae29a–0xae2a4`; CSV does the
  same at `0xae18a–0xae194`. `Com_UngetToken` (`_Com_UngetToken`) copies
  `0x3482a8` back into `0x3482a4` at `0xadfa3–0xadfa8`.
- Whitespace loop `0xae0cb–0xae0fe` uses signed byte comparisons (`cmpb/jg/jle`)
  against 0x20. High-bit bytes follow the whitespace path.
- Exponent path `0xae572–0xae58d` performs the store/input advance before its
  first digit test, including after the sign branch at `0xae594–0xae5a9`.

The Linux guide agrees on all four behaviors. The earlier discovery also read
`cmd.c` buffer execution, tokenizer, dispatch, registration and argument helpers;
no new implementation candidate was selected there. Existing WS47 tokenizer
corrections were retained. `Com_Compress` matched the inspected Mac path and
was left unchanged.

## Terminal exponent memory-boundary follow-up

Root review identified that reproducing Mac's unconditional exponent iteration
also reproduced its read past the string terminator for `1e`, `1e+` and `1e-`.
Mac `0xae564` loads the byte after the exponent marker; `0xae5a5` loads the byte
after an optional sign. Both enter `0xae572` even for NUL, store that NUL, then
advance and read beyond it at `0xae582–0xae585`. This is an original invalid
memory access, not a defined terminated-string token-consumption contract.

The fixture was extended before fixing this boundary: exact `strlen+1` heap
allocations for all three terminal exponent forms. The new `terminal` group
failed under ASan with a one-byte heap-buffer-overflow at `q_parse.c:555`,
exactly after the three-byte `1e` allocation. Existing proof cases were retained.

The minimal native correction breaks the exponent do/while when `c` is NUL,
before storage or input advancement. It returns the existing token text and
leaves the cursor on terminal NUL; the next parse returns empty and clears the
cursor. Non-NUL malformed forms still consume their first exponent character
exactly as Mac, and valid exponent behavior is unchanged. This deliberately
defines the native input memory boundary without adding exponent validation or
trying to emulate bytes outside the caller's string.

Caller inspection found punctuation mode explicitly enabled in material,
statemap and technique loaders reading `FS_ReadFile` buffers. No parser API
contract guarantees a readable byte after NUL. Inspected server/entity/script
file callers use default space-delimited parsing; no server exponent trigger
was demonstrated.

Re-ran the complete new fixture with both stock and CoD2x engine databases using
the commands above: all five groups passed under ASan/UBSan, including all three
exact-sized terminal allocations and the retained non-NUL malformed exponent
cases. Repeated OFF `unifdef`/`cmp` and `git diff --check`: both passed. Compiler
lane released again; no commits or index changes.
