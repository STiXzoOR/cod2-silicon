## Launch ownership and engine contracts

`LauncherModel.configStudio` exposes an observable, main-actor `ConfigStudioSession`. Its store stays private: UI disk operations and launch/attach/exit transitions use synchronous main-actor methods. Idle boot calls `initialize` after parsing forwarded arguments, so Main and its migrated values are available for editing before the first game launch. Initialization does not reserve a launch; attached games defer migration. A thread-safe store guard checks launch reservation, every tracked PID and a fresh discovery probe. The root polls its installed helper applications every 250 ms, tracks every matching helper plus its owned `Process`, refreshes observed config bytes while running, and restores the launcher only after the final process exits. The probe closes the interval before the poll observes a new attached process. Discovery matches the current bundle's `.game` identifier and exact resolved helper executable; it does not attach unrelated installations or arbitrary standalone executables.

`prepareLaunch` passes the full `GameSettings.dvars()` result to `ConfigPersonalValues`. DPI is metadata; an advanced `dpi` command is rejected. Migration failure returns the complete legacy launch mode and publishes `migrationError`; it never claims migration succeeded. Once `ConfigMigration.run` succeeds, the selected profile supplies personal values, including advanced personal overrides. Display, filesystem/startup, port and housekeeping values remain in argv and `launcher.cfg`. Explicit forwarded arguments, demo playback, onboarding and Apple-event link delivery retain their existing paths. Chain/path preparation errors after successful migration stop launch instead of silently forcing personal values again. Successful migrated launches require a saved session baseline; a legacy fallback can continue with a visible archive error if its store is unusable.

Migration source selection is explicit and limited to the writable home:

| Source | Selection rule | Required engine contract |
| --- | --- | --- |
| `.flattenedLegacy` | CoD2x dialect and existing `<home>/main/config_mp.cfg` | Imports the previous shared native CoD2x config into a new Main profile and preserves the shared original. Subsequent launches require WS102's repaired per-profile contract. |
| `.profile(id)` | No shared CoD2x source; valid `main/players/active.txt` selection | Stock main-profile behavior, or WS102 CoD2x: first active token selects `main/players/<id>/config_mp.cfg`. The source profile remains intact. |
| `.emptyHome` | No selected profile, no profile configs; F2 also checks for an unexpected shared file | Fresh stock main-profile behavior or WS102 CoD2x per-profile behavior. |

Existing unselected profiles are not guessed into a migration source. An invalid/missing active profile or conflicting migration journal preserves legacy launch behavior with an error. Both dialects have focused fresh/profile tests. The current app wrapper constructs `.cod2x`, matching the repository's CoD2x-only app builder. A stock wrapper must construct `.stock`. Effective `fs_game` includes advanced settings and forwarded `+set`/`+seta` values. Stock nonempty-mod homes are outside F2's main-only ownership API and explicitly retain legacy mode; CoD2x assumes WS102 keeps profile ownership in main independently of the mod.

**Integration dependency:** the released CoD2x engine still collapses profile config paths into `main/config_mp.cfg`. This branch deliberately does not compensate by flattening profiles or editing the engine. Do not ship Config Studio's per-profile launch mode against that engine without WS102. Synthetic launcher tests prove launcher paths/ordering, not the unrepaired engine's profile support or arbitrary mod search behavior.

`ConfigStudioLaunch.chainBasename(profileID:)` is the shared B2/F3 naming contract: `cs_` plus the first 160 bits of SHA-256 over the ASCII identifier lowercased, as 40 hex characters, plus `.cfg` (47 bytes, below the engine path limit). This handles all F2 identifiers, preserves case-insensitive identity, and avoids punctuation-substitution aliases. `GameLaunchPlan` validates the profile and exact derived basename, rechecks that the regular chain file exists under `<home>/main`, and then appends `+exec`. No chain editing was added. B2 must use this helper instead of concatenating raw profile IDs. Engine search of main chains under particular mods remains an engine integration check.

## Session history and conflicts

Before a launch, `.studio-game-session.json` privately archives every existing profile's exact config/sidecar version and a session UUID. Tracking all existing profiles allows an in-game active-profile change to be recorded too. A launcher restart reuses that archive when it attaches to the game. An attached process without an existing archive gets the first observed version as its baseline; that cannot reconstruct changes from before attachment. On exit, profiles first created by the game receive a Game session row with empty before-config bytes and absent before-metadata, representing no captured previous config. Deleted profiles are not recreated and cannot block a later launch. The source's `deletePlayerProfile`/`Com_DeletePlayerProfile` path established that this is a real in-game lifecycle case; its use of fs_basepath for deletion also needs review in the engine profile-path unit, outside this launcher's synthetic contract checks.

`recordGameSession` runs only after the last tracked/discovered game exits. It never rewrites the game's config. An unchanged profile adds no history row. Changed profiles use the durable session UUID; repeated notifications and interrupted retries cannot add duplicate rows. A conflicting exit-time transaction keeps the archive and is retryable through `finishSession()`. The archive is removed only after every surviving/new profile has been recorded successfully. These are tested filesystem contracts, not a claim of physical power-loss durability or exclusion of an uncooperative writer racing a rename.

Refresh publishes current disk data without replacing the user's draft or its expected version. A stale save remains a conflict after refresh. For an interrupted transaction, `inspectRecovery` returns the exact current version and journal bytes; `keepDiskVersion` checks that receipt again, archives the journal under the profile's `recovery/`, removes its staged history row and pending journal, and preserves the external config/sidecar. The draft remains available. Explicit `rebaseDraft(on:)` lets the UI reapply a reviewed draft against a displayed current version; ordinary refresh never rebases it. This disposition refuses writes while a game runs.

## Exact API for the UI agent

Bind directly to `LauncherModel.configStudio` with an observed session object. It is optional for preview mode and initialization errors; the root exposes initialization errors through `notice`. No raw `ConfigProfileStore` is exposed. All methods below run synchronously on `@MainActor`, throw actual store/document errors, and should be invoked once per committed gesture.

| Surface | API |
| --- | --- |
| Read state | Published private-set `profiles: [ConfigProfile]`, `current: ConfigProfileRead?`, `history: [ConfigHistoryEntry]`, `draft: ConfigDocument?`, `draftProfileID: String?`, `error: String?`, `migrationError: String?`, `migrationCompleted: Bool`, `runningPIDs: Set<Int32>`, `launchReserved: Bool`, `recovery: ConfigTransactionRecovery?`; computed `isReadOnly`, `hasDraft`, `home`. |
| Refresh/draft | `refresh()`, `setDraft(_ document:)`, `discardDraft()`, `saveDraft(metadata:source:summary:)`, explicit `rebaseDraft(on: ConfigProfileVersion)`. A draft retains its original profile ID when the game changes active selection. |
| Committed edit/metadata | `update(document:metadata:summary:)`; supplying the unchanged document supports rename, notes, locks and DPI metadata gestures. A failed save retains its draft and version. |
| Loadouts | `selectProfile(_ id:)`, `createProfile(id:displayName:document:) -> ConfigProfileRead`, `duplicateProfile(as:displayName:) -> ConfigProfileRead`. Selection refuses an undisposed draft. Creation/copy does not silently select the result. |
| History | `restore(snapshotID:revision:)` (`.after` by default, `.before` for undo), `finishSession()` to retry exit capture. Restore refuses an undisposed draft and uses current expected bytes. |
| Journal recovery | `inspectRecovery(profileID:)`, then explicit `keepDiskVersion()`. `ConfigTransactionRecovery` carries `profileID`, `current: ConfigProfileVersion` and exact `journal: Data`. Refresh alone does not cancel a journal. |
| Root lifecycle only | `initialize(settings:forwarded:)` for idle boot without a launch reservation; `prepareLaunch(settings:forwarded:) -> ConfigStudioLaunch?`, `cancelLaunch()`, `gameLaunched(pid:)`, `reconcileGames(_ pids: Set<Int32>)`. A failed process start must cancel its reservation. Views should use the root's existing play/connect/deploy methods. |

The UI owns navigation, editor/control presentation, filtering/search, comparison, lock policy, undo presentation and confirmation for explicit recovery/reapply. This unit creates no buttons, synthetic product loadouts or new views. Mutating in-memory draft text itself does not write game data; every disk mutation uses the guarded store.
