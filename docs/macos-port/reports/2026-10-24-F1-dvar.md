# F1 dvar domain, conversion and mutation reconciliation

Baseline: `6c6edd0343259966e2697c8ca561fe6d1c2c5cbe`, shared branch
`decomp/f1-shared-wave2`. This worker changed only `src/PC/universal/dvar.c`,
`tests/lp64/dvar/f1_domain.c`, `tests/lp64/dvar/f1_run.py`, and this report.
No staging or commits; the parent owns canonical verification and integration.

## Changed behavior

`behavior_changed: true`, native stock and CoD2x only.

- Float/vector domain tests now use the Mac's ordered less-than/greater-than
  rejection. Unordered NaN comparisons do not reject a value. Existing finite
  bound checks are retained.
- External string promotion to float/vector now clamps positive and negative
  infinity to the upper and lower bounds, and preserves NaNs. The prior native
  helper substituted the reset value for every nonfinite input. It originated
  in the initial repository commit; searches found no documented dvar platform
  safety exception. This restores original behavior rather than introducing a
  new sanitization policy.
- An enum string that misses all exact names and contains a nondigit now fails
  immediately. Previously native code tried prefix matching and accepted values
  such as `bri` for `bristol`. The original does still attempt prefix matching
  after an out-of-range all-digit index, e.g. `12` for `12long`; this is preserved.

No reference source or disassembly was copied into the repository. The Linux
1.3 dvar guide was read for control flow; implementation decisions were checked
against the owned Mac 1.3 binary.

## Mac evidence

- `Dvar_ValueInDomain` (`__Z18Dvar_ValueInDomainh9DvarValue10DvarLimits`,
  `0x50edc`): vector comparisons at `0x50f39/0x50f42`,
  `0x50f75/0x50f7a`, and `0x50fa6/0x50fab` reject only ordered greater-than.
  Scalar float at `0x50fbf` explicitly skips the lower-bound rejection on
  unordered input (`jp` at `0x50fc8`), and the upper comparison accepts it via
  `jbe` at `0x50fd4`.
- `Dvar_MakeExplicitType` (`0x52bc2`): inlined scalar clamp at
  `0x52fb9–0x52fd9` and `0x53081–0x53090` preserves unordered input and selects
  bounds for ordered out-of-range input. Vector clamp loops at `0x52f4b`,
  `0x52f82`, and `0x53014` do the same per component. There is no reset-based
  nonfinite fallback.
- `Dvar_StringToValue` (`0x512c6`): exact enum lookup at `0x51568`; digit test
  at `0x51340–0x5136a` branches directly to invalid sentinel `-1337` at
  `0x5136c`; only a completed digit sequence proceeds to index and prefix
  fallback (`0x51594`, `0x51516`).
- Retained an apparent original bug: `Dvar_SetVec2` tests type **4**, confirmed
  at `0x54bcf`. The Linux guide also documents it. It was not "corrected" to
  type 2 during this fidelity work.

## Coverage and limitations

Reviewed the core domain/clamp helpers, value/string conversions, current/reset/
latched storage, explicit type promotion, set-source protection, reset,
registration/re-registration and typed setter wrappers against the Linux guide;
Mac assembly was inspected for the changed paths, type promotion, validation,
string-to-value conversion and the suspicious Vec2 setter. This is **partial
file reconciliation**, not a claim that every function has independent Mac
coverage. Name/hash rules, all getter coercions, color corner cases, buffer
save/load, domain diagnostic formatting, unregistration, command wrappers and
all concurrency/lifecycle behavior still need exhaustive Mac comparison.
CoD2x's 4096-entry pool remains unchanged.

The parent requested investigation of a crash reading `showpackets->current`.
`Netchan_Init` stores the direct `Dvar_RegisterBool` result; registration returns
an address in static `dvarPool`, and ordinary dvar operations never free that
record. Shutdown clears count/hash but does not free the pool. No reproduced
pointer corruption or explanation of that crash was found here; the network
worker and parent were informed. No speculative transport/lifetime guard was
added.

No full engine build, game process, server replay or client comparison ran.
The overall faithful multiplayer finish criteria remain unverified. Native NaN
propagation is now faithful on these paths; downstream consumers were not
claimed safe for arbitrary nonfinite user input.
